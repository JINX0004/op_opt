# `mat_mul_v3` implementation-plan inventory for 910B3

This inventory examines the source at `../mat_mul_v3` in this workspace.
It counts **implementation-key combinations**, not the much larger number of
complete tilings. The scope is the legacy/non-advanced host selector used for
910B3. The separate `arch35` registry targets `DAV_3510`/`DAV_RESV`, not
the normal 910B3 route ([dispatch](../mat_mul_v3/op_host/op_tiling/matmul_v3_tiling.cpp),
[advanced architectures](../mat_mul_v3/op_host/op_tiling/matmul_v3_platform_common.h)).

## Count and meaning

The code path is: [host entry](../mat_mul_v3/op_host/op_tiling/matmul_v3_tiling.cpp)
selects the legacy tiler; [`DoOpTiling`](../mat_mul_v3/op_host/op_tiling/matmul_v3_base_tiling.cpp)
at lines 719–760 uses a bank hit or builds a basic tiling; `DoBasicTiling`
calls `DoSelectTiling` at lines 669–717; `DoLibApiTiling` copies the chosen
tile fields and creates the key at lines 2755–2795; and
[`mat_mul_v3`](../mat_mul_v3/op_kernel/mat_mul_v3.cpp) dispatches that key
to a concrete kernel body. The 910B3 route is separate from `arch35`.

There are **eight auto-generated `(full-load mode, split-core mode)`
combinations**, plus **one repository-only atomic multi-core split-K
combination**. The modes are defined in the
[host enums](../mat_mul_v3/op_host/op_tiling/matmul_v3_common.h)
and [kernel key](../mat_mul_v3/op_kernel/mat_mul_v3_tiling_key.h).
The [kernel dispatch](../mat_mul_v3/op_kernel/mat_mul_v3.cpp)
confirms that these combinations have executable bodies, subject to
compile-time dtype/format gates. A scan of its `LOADMODE` and
`SPLITCOREMODE` conditions finds exactly nine distinct pairs.

| # | Full-load / split-core key | Execution plan | Generated by |
|---:|---|---|---|
| 1 | BASE / BASE | Output tiles distributed over cores; each core reduces its owned C tile across K | Basic fallback, including L2 blocking |
| 2 | AL1_FULL_LOAD / BASE | Keep A in L1; stream/reuse B for output-tiled work | `DoAL1FullLoadTiling` (FP32 and narrow M) |
| 3 | BL1_FULL_LOAD / BASE | Keep B in L1; includes output-align/Fixpipe and special core-split variants | `DoBL1FullloadWithFixpipeTiling`, `DoBL1FullLoadTiling` |
| 4 | BASE / SINGLE_CORE_SPLIT_K | K loop and partial-output handling within each output-owning core, MKN order | `DoSingleCoreSplitKTiling` |
| 5 | BASE / SINGLE_CORE_NKM_SPLIT_K | Single-core split-K with NKM loop/preload order | `DoSingleCoreSplitKTiling` via `CheckSingleTilingOk` |
| 6 | BASE / SINGLE_CORE_SPLIT_K_GM_TO_L1 | Single-core split-K with a GM-to-L1 path | `DoSingleCoreSplitKTiling` via `IsGmToL1ByShape` |
| 7 | AL1_FULL_LOAD / SINGLE_CORE_SPLIT_K | Combined A-in-L1 and single-core split-K program | `DoSingleCoreSplitKAL1FullLoadTiling` (FP16/BF16 case) |
| 8 | BASE / DETERMINISTIC_SPLIT_K | Cores own K slices; AIV reduces workspace partials deterministically | `DoDeterministicMultiCoreSplitKTiling` |
| 9 | BASE / MULTI_CORE_SPLIT_K | Cores own K slices; synchronized atomic accumulation into C | Repository/AOE tiling only, FP32 with `transA=false`, `transB=true`, one round |

Evidence for the eight generated combinations is in the
[first-success selector](../mat_mul_v3/op_host/op_tiling/matmul_v3_base_tiling.cpp):
`DoSelectTiling` at lines 1406–1432, the full-load methods at 1833–2049,
single-core split-K at 2375–2525 and 2945–3020, and deterministic split-K
at 2535–2729. `DoL2CacheTiling` at 2093–2132 returns `false` after setting
L2 parameters, so it does **not** terminate selection as a separate kernel
family. The atomic mode is accepted only from `GetTilingFromRepo` and checked
at lines 732–753; `DoSelectTiling` does not create it. The included B3
knowledge bank has 13 records with `tilingEnable` values 0, 2, or 3; it
does not demonstrate an atomic record, although the route is implemented.

The count is intentionally at the *key-combination* level. `FIXOPTI`,
ND-to-NZ preprocessing, K shift, output conversion, transpose/dtype
specialization, L2 order, and the BL1 core-split path may alter the event
timeline while retaining the same full-load/split-core pair. A complete plan
also includes `usedCoreNum`, `singleCoreM/N/K`, `baseM/N/K`, `stepM/N/Ka/Kb`,
`depthA1/B1`, `dbL0A/B/C`, `iterateOrder`, L2 tile parameters, and workspace.
These are passed in
[`TCubeTiling` and `MatmulTilingData`](../mat_mul_v3/op_kernel/mat_mul_v3_tiling_data.h)
or copied from the tuning bank at lines 1058–1103 of the host selector.

## Selection behavior relevant to optimization

The current non-bank path computes a basic plan and then calls
`DoSelectTiling` ([lines 669–760](../mat_mul_v3/op_host/op_tiling/matmul_v3_base_tiling.cpp)).
The `DO_CACL_TILING_ENABLE` macro breaks on the first method returning true,
so the code chooses by priority and eligibility, **not by evaluating predicted
runtime across alternatives**. A bank hit returns before this selector.

The source mixes hard requirements and performance heuristics. Examples of
hard conditions include compiled dtype/format combinations, instruction and
alignment support, L1/L0/UB capacity, output coverage, workspace, and the
atomic one-round restriction. The `K >= 27392` trigger, the
`singleCoreN < 512` rejection, and the `avgRatio < 0.7` rejection are
performance heuristics ([single-core support](../mat_mul_v3/op_host/op_tiling/matmul_v3_base_tiling.cpp)
at 2320–2373 and 2438–2463); they should rank or seed candidates rather
than define mathematical feasibility unless a separate correctness limit is
proved.

For the earlier FP16 NN example `(M,N,K)=(16,16,102400)` on 20-AIC B3,
the AL1 full-load FP32 gate and combined AL1/split-K large-N gate fail;
ordinary single-core split-K reaches the small-`singleCoreN` rejection.
Deterministic multi-core split-K passes its long-K/few-MN-tiles heuristic
(`K >= 20*384`, one spatial tile). Thus the built-in path is expected to
select deterministic split-K, barring a bank hit or an earlier special
gate. A model-based selector should still compare it with legal BASE plans.

## How to make this an optimization domain

1. Represent a candidate as `(fullLoad, splitCore, fixOpti, nd2nzMode,
   specialOpti, tilingData, L2 policy, reduction policy)`. Use the kernel
   dispatch as the whitelist of compiled combinations.
2. Refactor each candidate builder to start from the same immutable workload
   and hardware state. The existing methods modify `runInfo_`, `args_`, and
   `tilingEnable_`; trying them sequentially without restoring state would
   contaminate alternatives.
3. Separate **legality checks** from heuristic cutoffs. First retain every
   candidate that has a compiled kernel, correct coverage/numerics, sufficient
   local memory, and valid workspace. Keep the current first-success path as
   a fallback and a source of early feasible candidates.
4. For each complete legal plan, estimate the end-to-end timeline. Include
   conversion/ND-to-NZ events, L1 full-load residency, loop and L2 order,
   output handling, and split-K workspace plus reduction/atomic costs.
5. Enumerate this finite family set initially. Add branch-and-bound only when
   independent tile/buffer choices make full enumeration expensive; report
   the chosen key, complete tiling, predicted runtime, and optimality gap.
   Section 10 of [the mathematical model](README.md) gives the objective and
   valid-pruning rule.

This analysis is source inspection only. It does not establish which plan is
fastest on actual 910B3 hardware or validate that every possible key is
compiled for every dtype/format binary.

# Why FP32 512×512×27328 favors BASE in MatMulV3

This note uses the [same-shape device-4 measurements](results/comparison.csv)
and the exact isolated 910 source build used in that experiment. The local
`mat_mul_v3` snapshot differs from that build, so source references below
refer to `/home/xianfei/solvebase_bench_20261025/ops_nn_source_build/matmul/mat_mul_v3`
on 910 (commit `b2cdb471`, plus the research-only family switch). Model
references refer to the 910 branch at
`/home/xianfei/dev/ops-nn-sribd-mip-selector/experimental/mip_selector/model`.

## Observed result

| Path | Core tile M×N×K | Base tile M×N×K | Spatial panels | AICs | Measured median | Model score for this exact source tile |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| Source BASE | 112×128×27328 | 112×128×64 | 5×4 = 20 | 20 | **220.06 µs** | 232.42 µs |
| Forced source deterministic Split-K | 384×512×192 | 128×128×64 | 2×1 = 2 | 20 split along K | **265.59 µs** | 250.99 µs |
| Model's best BASE | 128×128×27328 | 128×128×64 | 4×4 = 16 | 16 | unmeasured | 251.43 µs |
| Model's best Split-K | 128×128×64 | 128×128×64 | 4×4 = 16 | 20 split along K | unmeasured | 232.35 µs |

The forced Split-K kernel is **20.69% slower** than source BASE at the same
shape. Both rounds show the same direction: BASE 219.77/220.34 µs, Split-K
265.98/264.99 µs. The unforced source chose BASE. The experimental force
switch bypassed `SupportMultiSplitK()`'s shape-selection threshold; it did
not change tile generation or the device kernel, and the output check passed.
The source threshold is K=27392, so this K=27328 case would not enter the
deterministic branch unforced. That threshold is a selection heuristic here,
not evidence that the forced kernel is invalid.

## Why the optimizer reverses the source-family ranking

The remote model's `SourceCompatibleDomain()` sets
`base_core_equals_base=true`. `TileValues()` includes 112 as a **core**
extent (`ceil(512/5)` aligned to 16), but the default **base** grid is
16/32/64/128/256. Since BASE must have `core=base`, the source's 112×128
BASE tile is excluded. The model's chosen 128×128 BASE tile creates only
16 output tiles, leaving four of 20 AICs unused. At the experimental FP32
Cube rate of 3.6 million FLOP/µs/AIC, the busiest core's compute lower
bound rises from **217.65 µs** (112×128) to **248.75 µs** (128×128).
This explains most of the model's 251.43 µs BASE score. The actual source
BASE time, 220.06 µs, is close to the 112×128 compute bound.

The remote `SolveSplit()` allows `stepK=1` and arbitrary spatial geometry.
It selects 128×128×64, whereas the source's `SetBasicBlockOfMK33()` fixes
base 128×128×64, `stepM=3`, `stepKa=stepKb=3`, then emits
384×512×192 for this shape. With 20 K cores, the model's winning plan has
`ceil(ceil(27328/64)/20) × 64 = 1408` K elements on the busiest core;
the source's 192-element slices give `ceil(ceil(27328/192)/20) × 192 = 1536`.
The model's plan therefore has 8.3% less critical-core K work. It also
models four 128-row panels with reduction overlapped against subsequent
Cube panels; the source has two panels, 384 and 128 rows. These timing and
overlap assumptions make the **unvalidated** free-search Split-K candidate
score 232.35 µs. The source tiler does not emit that candidate in this path.

When the model scores **the two tiles that the source actually emits**, it
already ranks BASE correctly: 232.42 versus 250.99 µs. The remaining
fixed-tile errors are +5.6% for BASE and −5.5% for Split-K. They compound
the decision gap but are smaller than the domain differences. Adding only
the 112×128 BASE tile would still leave its 232.42 µs score
almost tied with the model's free Split-K score of 232.35 µs. Both families'
search domains must therefore be brought into line with source-emittable
plans; a single BASE-grid addition is insufficient.

Split-K's source kernel writes FP32 partials to workspace and uses AIV reduction with
cross-core synchronization; BASE writes the result without that reduction.
The reduced model includes a partial-add term, but its one-stage overlap and
inherited vector/synchronization parameters do not reproduce every source
kernel step. The 14.60 µs Split-K underprediction cannot yet be assigned
to a specific primitive without separate Cube/AIV profiling.

## FP32 model versus the source implementation

The model handles FP32 element width (four bytes), FP32 accumulator/output,
the source `baseK=64` for deterministic Split-K, and the extra workspace for
FP32 partials. The experiment has `nd2nzA=nd2nzB=0`, no bias, and HF32
disabled; the source kernel sets HF32 off. There is no indication of a
wrong dtype or a hidden conversion path in this comparison.

There are important implementation differences:

1. **Tile legality and source rules:** the model's generic grid excludes
   BASE baseM=112 while admitting Split-K core128/stepK1; MatMulV3's
   deterministic branch uses its MK 3×3 tile and L1 depths. This is the
   primary reason the family ranking reverses.
2. **BASE K-read requests:** source BASE has `stepKa=stepKb=4`, so each
   operand uses about `ceil(27328/(4×64)) = 107` L1 windows per output tile.
   The default model charges `ceil(27328/64) = 427` request startups.
   A diagnostic FP32 K-step variant scores this source BASE tile at
   **220.33 µs**, close to 220.06 µs measured, versus 232.42 µs by the
   current scorer. This correction is *not* ready globally: the same variant
   greatly underestimates small FP32 BASE tiles.
3. **Split-K reduction and overlap:** the source kernel synchronizes AIC/AIV
   and reduces FP32 workspace partials for each spatial panel. The reduced
   formula represents this as a serial partial-add chain with idealized
   overlap between panels. Its vector-add and `split_partial` primitives
   were inherited from the FP16/BF16 calibration, while the FP32 Cube rate
   was fitted from one large BASE tile. This limits FP32 transfer/reduction
   accuracy despite the correct byte widths.

The source code locations supporting these points are
`op_host/op_tiling/matmul_v3_base_tiling.cpp` (`SetBasicBlockOfMK33`,
`SupportMultiSplitK`, `DoDeterministicMultiCoreSplitKTiling`) and
`op_kernel/mat_mul_deterministic_splitk_kernel.h`
(`MatMulKernelDeterministicSplitK`, `ReduceKInUbL2cache`). The model paths are
`mip_solver.cpp` (`TileValues`, `BaseStageUs`, `SplitStageUs`, `SolveBase`,
`SolveSplit`) and `hardware_profile.h` (`ExperimentalFp32910B3`).

## Model changes to test next

Represent the source's FP32 BASE 112×128 tile and deterministic MK 3×3
step/panel constraints in a source-emittable decision domain. Re-score both
families using exact source tiles first; only then widen the domain with
tiles that can actually be emitted and validated on device. Separately
calibrate FP32 BASE L1-window startup and Split-K AIV reduction. A revised
domain/objective should be checked on held-out shapes before enabling the
FP32 online selector.
